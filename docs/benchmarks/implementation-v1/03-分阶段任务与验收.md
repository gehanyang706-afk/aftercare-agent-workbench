# 分阶段任务与验收

版本：2026-10-20 / v1。旧项目阶段0—6A继续保留；本升级使用U0—U6命名，防止覆盖原交接和审批。

## 总安排

| 阶段 | 主要交付 | 是否用真实模型 | 推进规则 |
|---|---|---|---|
| U0 | 工作区/资源/源码基线、接口清单 | 否 | 自主完成 |
| U1 | 官方适配、基线、统一预算角色、离线合同 | 否 | 验收后继续 |
| U2 | Trace/metrics、上下文策略基础、校准计划 | 否 | 准备具体批准材料 |
| U3 | 小批校准、开发迭代与有限消融 | 是 | 每个冻结批次另批 |
| U4 | 本地真实PG并发/进程故障实验 | 否 | 环境齐备后自主做，可与等待U3批准交错 |
| U5 | 冻结Test40×2 | 是 | 额度和独立批准齐备才执行 |
| U6 | 报告、镜像、复现与面试交接 | 仅整理已有结果 | 完成后停止扩展 |

每阶段在docs/handoffs/upgrade-Ux.md中记录：改动/复用、验证命令和结果、版本、未覆盖项、下一步及一条完整机制。每个命令必须实际运行后才能写通过；代码路径建议不等于已创建代码。

## U0：先把起点固定下来

1. 阅读项目AGENTS和两篇已有benchmarks文档；检查当前分支、HEAD、worktree和未提交改动。不要覆盖已有报告编辑或未跟踪设计文件。
2. 新增升级范围说明：普通离线开发可继续，旧真实六题待批计划本轮不执行。保留所有历史权限、账本与holdout边界。
3. 建开发分支，保存当前源码/依赖/报告hash基线；不为建分支自动stash、回退或清理。
4. 盘点当前Python、PG、Docker、本地源码/镜像、benchmark依赖是否存在；缺什么列清单。依赖锁和产品环境隔离。
5. 核对固定官方接口与统计元数据；不阅读Test题正文。先生成upstream.lock.json和scope-map.md。

验收：能清楚列出哪些代码复用、哪些新增；用户原修改hash不变；source tree有新升级范围；默认真实开关未改变。此阶段无需重新全量跑237项测试，只在后续触及功能时跑相关验收。

## U1：官方接口与受控传输

按01文件实现adapter/baseline/source_guard与ExperimentGateway。

先做完全离线protocol fixture：模拟用户消息、一次读工具、多tool批次、写工具、工具错误、文本终止；通过官方Orchestrator和评分入口运行，固定假模型仅验证接口。任务来自合成测试或train，不用test oracle。

实现episode-role持久映射和新计划类型；测试Agent/User同模型也会合并扣精确模型额度，新角色、源码hash变化、批次重启、预算并发都无法越过上限。

增加模型入口清点表：官方agent调用、用户模拟器调用、NL评审、review、遥测/缓存。关闭未批准项；通过transport spy和网络禁止验证实际无旁路。

官方基线使用LLMAgent，不用GT/solo；工具真正由官方环境执行。只按可见内容构造状态，不把Task对象送入Agent。

验收：
- 离线对话能到官方评分入口；无越权出网。
- 多工具消息ID保持配对，工具没有双执行。
- baseline请求形状保持原模板/能力，只施加共同限制。
- Agent/User/Judge角色隔离；预算失败与未知usage反例通过。
- 产品九工具和原批准契约回归通过；benchmark开关不能打开Web真实入口。

完成后保存checkpoint提交，只包含本次文件；用户原改动留在原处。

## U2：测量先行及最小上下文候选

1. 完成统一Trace、逐题CSV/JSON、配对统计与not_run状态。
2. 实现full_history和按完整交互块的fixed_window；evidence_projection先支持通用投影和来源结构，不先编大量业务启发式。
3. 使用合成/已有train可见轨迹验证消息配对、跨轮事实、改口、多个实体、不可压缩失败和原始审计不变。
4. 冻结20个train ID开发池和默认4+4实际开发计划。只读ID做划分，记录读取过的训练任务。
5. 生成U3-calibration待批manifest：2题×2配置，列Agent/User所有请求、Token、输出和时间上限；写明无评审或说明确需的额外角色。cap根据离线请求尺寸制定，未知字段不能发送。
6. 完成至少一条产品profile的纯函数策略接入验证，避免两套不相关实现只共享项目名。旧默认profile保持可回退。

验收：输入同一合成结果两次统计一致；负收益、早失败、缺usage、部分运行的指标不会被美化。校准计划可审查但没有批准文件、没有真实账本新请求。

此时可以集中请求第一次真实校准批准，同时继续U4。不要为了等待批准反复重跑不变的全部测试。

U4若修改了共享源码，应在真实校准前重新冻结U3计划，原hash与批准不再有效。真实批次运行期间暂停共享工作树的编辑及同库测试；需要继续独立开发时采用隔离工作树与测试库，不能影响被冻结的执行环境。

## U3：用Train驱动优化

### U3a 兼容与成本校准

拿到精确计划批准和账户确认后，只跑固定4个episode。输出两组实际输入、官方工具事件、评分、Agent/User分别用量与停止原因。

若协议失败，不直接追加题目；离线修复后新版本重新提交计划。业务失败可以保留，因为校准并非要求高成功率；但要有足够的完整交互路径来估算长任务成本，提前失败的均值不能代表成功任务成本。

### U3b 一轮主候选

在预先固定4个tune任务上比较official_tc与harness_evidence，前提是U3a和离线轨迹支持上下文问题值得处理。只改一类主要机制，记录失败假设、变更、预期影响、反例和实际差异。

可检验假设示例：过期订单快照导致错误目标、同一工具返回重复占据上下文、裁剪后遗漏原始确认。不要先断言“动态状态一定更好”。

重复读取优化若不满足01中的新鲜度与官方执行边界，跳过。不要一轮同时增加新Planner、反思、工具缓存、政策检索和提示词。

### U3c 冻结开发验证

候选最多两轮。选定后在未用于这次调参的validation_pool固定4题做同模型对照；如开启消融，明确只关闭一项变量，所有角色费用计入。

若验证失败需要继续修改，后续不得再将已看过的validation题称为未见。两轮无益停止调参，交付结果，不强行跑出提升。

向用户提交正式Test预计消耗、当前额度缺口、候选版本和40×2计划。未经批准不运行Test。

## U4：固定Fault Injection Suite

### 环境与机制

- 仅使用明确验证过的aftercare_test；每组使用隔离fixture，不清空aftercare_demo或真实账本，不运行docker down -v。
- 复用本地PG和现有镜像，使用脚本模型或fake transport。测试本身不得发真实模型请求。
- 不同用户库存竞争时，各自拥有不同订单、共享目标SKU。禁止把跨用户访问同一订单的权限拒绝误当库存竞争。
- 在领取、事务开始前、事务提交后、checkpoint写入前、job收尾前设置可观察同步屏障；通过事件/管道协调，不用随意sleep碰运气。
- 启动真正独立的worker进程；只给测试创建且记录PID/启动时间的进程发信号，回收其子进程组，禁止killall或杀用户服务。
- 对每个故障检查injected、actually_occurred、recovered/invariants分别是否成立。只配置故障不算覆盖。

### 预定12组，每组20次

| 组 | 条件/触发 | 核心断言 |
|---|---|---|
| F01 | 同一client_message_id并发8次 | 一条用户消息/一个对应job；不重复增加意图版本 |
| F02 | 同一有效批准并发2次 | 唯一operation/application/预留；返回同一回执 |
| F03 | 同一有效批准并发8次 | 与F02同不变量，检查事务冲突处理 |
| F04 | 2个用户竞争最后1件 | 仅一个合法申请成功，无负库存/越权 |
| F05 | 8个用户竞争最后1件 | 同上，逐个记录成功或明确拒绝 |
| F06 | 新意图先于旧方案提交生效 | 旧批准失效，旧方案无副作用 |
| F07 | 原提交先完成，随后用户改口 | 原回执保留，不伪称撤销；新诉求独立处理 |
| F08 | 事务提交后丢响应 | 查询原操作恢复，仅一次副作用和匹配告知 |
| F09 | 领取后/提交前杀父worker，检查仍存活子进程 | 持久任务可回收，无孤儿造成错误或重复业务，完成清理 |
| F10 | 提交后/checkpoint前杀执行进程并重启 | 原操作查回或幂等恢复，不产生第二申请/库存变更 |
| F11 | 租约到期，接管后旧owner恢复 | 旧owner不能覆盖新owner任务状态；事务边界与唯一副作用正确 |
| F12 | SSE断线、重连和重复游标 | 消息重放不执行Agent/业务；客户端事件去重，最终回执一致 |

M定义为实际触发且全部预定重复满足不变量的组数；总重复次数预定240。无触发、任意一次失败、基础设施错误均如实报告，不把重跑后通过覆盖第一次失败。修复版本可重跑同组，旧版本结果另存。

F09必须区分杀父进程和杀子进程，子进程仍可能执行；只重建Python对象不算进程崩溃。F10的故障必须位于真实COMMIT之后，以独立DB连接看到操作行为证据；不以日志“即将提交”代替。

F11不得用“检查过lease”证明之后不会过期。若发现旧owner非法推进，再最小增加fencing generation/事务CAS；接管与提交谁先线性化须有证据。已经合法完成的副作用不因为后来lease过期就当作应回滚。

F11先复核父worker的会话advisory lock与子run_turn的执行锁。单纯SIGSTOP父进程不会释放数据库锁，不能据此假定已完成接管。建议在受控屏障暂停旧执行子进程，真实结束父worker及其租约数据库连接，但保留被记录的旧子进程；等租约到期、新worker实际领取并产生新owner（若实现generation则记录它）后，再恢复旧子，观察事务和任务收尾行为。记录锁、数据库会话及进程生命周期，禁止直接修改lease_owner假造接管。若执行锁正确阻止新旧子同时推进，就报告被串行化的实际路径；不为展示fencing制造生产中不可能的状态。此实验允许暂留旧子只为触发窗口，最终必须回收全部测试进程。

每组输出case_id、seed、concurrency、repeat、实际注入点、PID/进程生命周期、事务结果、operation/application/reservation计数、库存前后、消息/批准/回执关联、Trace与停止信息。断言从独立数据库读回，不采信模型文本或HTTP200。

### 可选的小型后端性能探针

正确性全部验证后，有时间才做：同机固定资源，2/4/8客户端，每档预热50、测量200次无模型HTTP请求；将只读快照、幂等回执重放、新业务事务分开，逐类报告p50/p95、错误数和样本量。

新业务事务要用独立可办理fixture，不能把大量重复确认快速返回当成新增事务吞吐。该探针只说明本机后端，不宣称Agent在线QPS或生产SLA；未执行就不写简历性能数字。

### 验收与修复

先盘点并引用已有有效测试，不重复造同样的单元测试。新增测试集中在真实进程边界、多owner竞争和断线恢复。故障触发失败应修测试装置；业务不变量失败才修产品。完成源码修改后跑受影响回归，阶段末运行必要全量测试一次。

## U5：最终官方Test

前置：U1/U2合同通过、U3候选已冻结、角色预算覆盖80episode、当前账户保护确认、正式计划批准。

只有可信runner加载Test所需任务/评分资料。开发实现者不预读答案；运行中不改实现，不查看失败后立刻修代码。固定40任务×2配置各一次，普通失败继续，预算/协议/安全/unknown按计划停。

完成后导出官方原始结果与统一账本核对；每个模型实际HTTP数必须可解释，包括用户模拟器。不要运行默认auto-review或补充NL诊断而未计费用。

指标按02文件计算；完整40题只在真正覆盖后报告。若发现适配错误需要新版本，首次结果留存；Test已见事实进入新报告，不能再次称全新盲测。

## U6：交付与停止扩展

提交以下资料：
- README短版：产品场景、核心架构、启动、实际结果、限制。
- 两张图：产品事务执行图；官方benchmark与预算/用户/评分边界图。
- official baseline、自定义Agent、纯离线合同、Fault Suite四条可复现命令。
- 依赖lock、上游commit/许可、源码与配置hash、逐题CSV/JSON、脱敏Trace样例。
- 公开Benchmark报告：实际任务数、成功数、A/B/C、配对任务、Agent/User用量及限制。
- 产品可靠性报告：M/12组、各组重复、真实触发与数据库证据。
- 5分钟演示：查询→预览→改口→确认→回执；再演示丢响应/刷新恢复。
- 面试交接：为什么官方环境不接自家PG、为何状态有来源、Checkpoint与业务回执区别、lease和幂等区别、如何避免失败省Token假象。

离线镜像只在变更确需演示时重建，沿用现有依赖层；不自动下载镜像或开放Web真实入口。用户报告原编辑保持。

结束条件是两条证据和复现交付完成，不是A/B/C必须正值。仅阻断安全/授权/副作用/计账缺陷进入必要修复；其他模型语言或小样本效果问题进限制清单，不自动新一轮调参。

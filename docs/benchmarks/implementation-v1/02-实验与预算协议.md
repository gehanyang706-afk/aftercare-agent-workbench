# 实验与预算协议

版本：2026-10-20 / v1。这里定义评测方法，不授权任何模型调用。数值上限必须在实际源码、模型、角色和任务确定后形成可审批manifest。

## 1. 数据划分与实验规模

固定上游v1.0.1及完整commit；官方Retail train74/test40/base114。开发、验证、正式评测明确分开。

从train ID以可复现规则抽20题作为开发池：按SHA256("aftercare-retail-20261020:" + task_id)排序，前12为tune_pool、后8为validation_pool。只根据ID选择，不看答案挑易题。写入manifest，核对两池不交叉且都属于train。

节省预算的默认路线：
- 校准：tune_pool前2题 × 官方基线/未优化适配器 = 4个episode。
- 第一轮优化：tune_pool预先固定前4题 × 基线/上下文候选 = 8个episode。
- 若确有具体失败假设，可做第二次通用修改，只对这4题运行新候选，另计4个episode；最多两次候选修改，不无限调提示词。
- 开发验证：冻结候选后，validation_pool前4题 × 基线/候选 = 8个episode；有额度再事先决定扩为完整8题，不能见分低后换题。
- 必要消融：仅当候选显示值得检验的效果且预算允许，在相同开发验证任务补一个关闭对应模块的配置。默认不做四套全矩阵。
- 正式Test：40题 × baseline/full，各一次 = 80个episode；任务、顺序、版本和共同限制先冻结。

最低默认路径共100个episode（4+8+8+80）；额外修改和消融会再增加。20题是候选开发池，不代表已执行20题。不得把多个variant/trial算成新的独立任务数。

数据预算若允许，可把真实开发量扩为12 tune/8 validation，但扩展须在相应批次前明确，不能见到结果再调整分母。Test只运行正式两配置，不把所有开发消融搬到Test。

## 2. 配置矩阵

| 名称 | 行为 | 主要用途 |
|---|---|---|
| official_tc | 官方LLMAgent，完整可见历史和policy，共同预算桥接 | 正式基线 |
| harness_full_history | 项目适配器，消息保持完整；只加共同Trace与治理 | 接口/传输等价校准 |
| harness_fixed_window | 保持完整policy、按完整交互块裁剪历史 | 可选开发参照 |
| harness_evidence | 带来源的工具结果投影和有效上下文装配 | 优先候选 |
| full | 从开发验证选出的候选别名 | 最终对照，不是所有模块默认全开 |

official_tc与harness_full_history原则上应有相同可见语义和基础指令；校准中若出现差异，先看序列化/消息/工具能力，不能立即称为优化提升。

不要人为截断基线policy、关闭其必要工具、给候选更多输出上限或隐藏目标。所有安全与费用保护两组共同存在，不把它们当作只对基线不利的条件。

## 3. 哪些变量保持一致

精确Agent模型版本、provider/地域、thinking与temperature等参数；精确用户模型与用户策略；官方commit、policy、工具schema、任务初态、奖励定义；单请求输出限额、请求/turn/token/time cap；缓存和重试设置；执行机器/并发配置；种子与每题次数。

共同上限是公平约束，不意味着随机对话一定消耗相同。模型用户会根据不同Agent实际回复自适应交互，不能强行回放同一条录音式回复。相同seed也不保证远端模型完全可复现。

每个task/config/trial都从全新官方环境开始，不能让第二组继承第一组的状态或工具缓存。按固定seed安排每题AB/BA顺序并交错执行，减轻服务时段影响；并发默认1，不并行增加费用波动。

日志注明API实际支持哪些参数；不支持seed就标注不可控，不伪造固定随机性。Provider前缀缓存若无法关闭，记录可见缓存字段并报告限制。

## 4. Benchmark与产品效果归因

正式公开分数只来自官方环境/工具/政策/用户/评分器。只有实际生效的适配器上下文和决策策略可以作为差异解释。

产品PG行锁、可信UI批准、SSE、Worker Lease与回执生成不在官方决策链路中时，不能拿它们解释公开成功率或Token变化。它们由独立本地可靠性表证明。

官方Retail完整policy与产品24条政策语料不同，因此本轮不做“Hybrid RAG提高Retail成绩”的叙事。若以后把官方policy改成检索，需要另立消融，保证规则可得并明确改变了什么；不纳入当前最低交付。

## 5. 每个正式计划的必填字段

run_id、batch_id、experiment_version、source_commit与source_tree_hash、上游commit、依赖lockhash、环境版本、模式和策略hash。

split、完整task ID清单及内容hash、variant清单、trial数、顺序seed、预定episode数；Test内容hash由可信准备脚本计算，不打印答案。

按角色列明：agent/user/judge/auxiliary是否启用、精确模型、provider/地域、thinking等模型参数、每请求输出上限、请求次数与Token额度。

还需：每episode总cap/角色cap、每用户轮或模型连续调用cap、单请求硬截止、episode截止、批次请求与Token总cap、批次墙钟、并发、HTTP/SDK重试、模型切换策略、额外费用上限。

评分：EvaluationType、reward_basis核验摘要、是否调用NL judge/auto-review、官方评分器hash和旁路诊断版本。

保护：本批账户确认标识、可用额度依据、免费保护；禁止隐式新role；旧批余量不转移；unknown usage规则；普通失败和硬停止规则。

缺任一费用/调用关键字段、值为null/待定或版本hash不一致，执行入口一律拒绝，dry-run可以成功但必须明确不可执行。

## 6. 校准和成本计划

公开数据不收费，不等于Agent与模型用户推理不消耗额度。先以4个episode测 Agent/User 各自的真实请求数、输入输出、历史增长、单步预留和耗时。

第一份校准cap由离线protocol请求样本估计：包含完整policy/schema、用户模拟器prompt和选定最大步数；据此给出保守预留，不沿用旧512输出、16/8次数、32k单题等值当作官方任务自然需求。共同输出上限若调整，要两组同样采用并纳入计划。

角色模型建议：Agent可继续使用已验证的精确Qwen版本；用户模型要明确选定并先验证官方用户协议。可同模型分角色，也可选择另一个已有额度的精确模型，但不能因为某题失败临时换用户模型。用户模型质量会影响任务难度，必须记录。

校准完成后估算：

    Agent费用/用量 = episode数 × 每episode Agent估计
    User费用/用量 = episode数 × 每episode User估计
    总量 = Agent + User + 已启用Judge/辅助调用

上限还需预留下一完整请求的空间，不能只拿实际平均量当可发送cap。对同一精确模型承担的角色合并对账。只知输入输出Token而价格未知时，报告Token不报告虚构人民币费用。

示例仅解释规模：若Agent平均12k、用户平均6k，正式80个episode就是约1.44M Token，其中Agent约960k。该例不是本项目预测；历史截图每模型1M不能保证足够，更不能据此自动购买或换模型。

实际额度不足时，先交付离线接入/真实已完成开发结果和缺口。可在正式Test前由用户明确批准减少范围或更改统一模型，但减少后只能称“固定Test子集”，不能写40题。不得先跑到预算耗尽，再选择已成功题报告。

三种真实批准类别：calibration、development/ablation、final-test。开发候选更新后重新冻结计划；可以一次批准明确列出的顺序子批，但不能用一个笼统总额度授权未知未来代码无限调参。

## 7. 普通失败与停止

普通任务未完成、工具合法业务拒绝、官方最大步数终止：按冻结协议记录该题结果，继续剩余固定题；不得现场改源码或重跑。

授权/hash/模型/地域异常、用量不明、额度或免费保护异常、安全边界异常、持久预算或硬截止触发：停止后续真实调用，保存第一次轨迹和未运行项。不要把异常转换成模型新的推理轮次。

未知usage计入保留预留，标明精确模型暂停；不能按零。进程死亡后可离线对账，不重新发送同一未知请求。

批次重启只允许恢复持久状态、导出结果和只读对账。未经计划明确支持的“继续未启动episode”不得自动启动；新批准如允许续批，也必须继续原计数与剩余总cap，不能重置。已有episode不重跑凑成功。

## 8. 结果与公式

每题official_reward及其组件原样保留，项目旁路诊断单列。官方任务奖励主要检查结果与必要告知，不能把参考动作匹配度当唯一成功要求。

完整Test已执行且有有效结果时：

    A_variant = 成功任务数 / 40 × 100%
    B = A_full - A_baseline（百分点）
    C = (1 - 全40题Full平均Agent Token / 全40题Baseline平均Agent Token) × 100%

全40题均包含失败消耗；Agent统计包含所有为其服务的规划/总结/反思调用。User/Judge单列但纳入总账。

同时报告双方均成功的配对子集：两组在相同任务上的Token均值/比值及任务数，避免提前失败造成“省Token”。另外列双成功、仅Full成功、仅Baseline成功、双失败四格计数。

若未完成全部40题，报告planned/attempted/completed/not_run、成功数/实际有效评测数，以及完成覆盖率；不把not_run伪装成模型任务失败或删掉后宣称完整官方40题成绩。对中途预算停止题保留官方可计算奖励与本项目execution_stop，明确二者的口径。

Unknown usage存在时不得发表精确成本节省百分比，可先报已知量与保留预留范围。对照差异可能是负数；不要把负B或负C改成“优化提升”。

一次40题中一题影响2.5个百分点。输出每组Wilson区间及配对差异区间（可选固定种子配对bootstrap），不把一两题优势称统计显著。仅一轮结果不能代表稳定性。

重复运行不是默认范围。只有预先批准每题n次，才按官方指标或组合估计报告pass^k；其含义是重复k次均成功的可靠性，与“至少一次成功”的pass@k不同。n<k时不计算该项。

## 9. 运行效率与后端性能的不同分母

记录Agent模型等待时间、用户模型等待时间、工具执行时间、评测耗时和端到端总时长。不能把“少了用户模拟器调用”全部算成Agent推理提速。

40题单次总耗时分布可报p50/p95，并注明样本量和包含用户模拟器；不是线上服务SLA。

后端HTTP延迟在离线脚本模型/无模型执行下单独测试，注明机器、并发、请求数和包含哪些操作。不得把无模型HTTP QPS当作真实Agent吞吐，也不把重复回执快速返回当作新订单提交吞吐。

## 10. 固定输出与验收

每批输出manifest、preflight、episodes.jsonl、episodes.csv、summary.json、report.md、账本对账及原始轨迹hash清单。失败/未运行都有行。

报告先给任务覆盖、每组成功数、配对胜负、Agent/User用量、停止情况；然后给失败类型和代表轨迹。内部机密不进Git，公开资料只提交脱敏摘要与复现方式。

metrics模块用人工合成数据测试：两组同成功率但失败组更省Token、缺usage、部分未运行、负收益、不同角色同模型、混合trial、重复导入。验证不会合并不同版本分母，也不会双计input/output与total。

## 11. 选型与终点

候选先看错误业务行为和任务效果，再看双方均成功成本。开发样本小，规则只是选型启发，不是统计保证。若两轮候选无益，保留官方/原实现，照实交付架构与负结果。

正式Test之后不按Test失败再调优并覆盖同次分数。确需安全修复时另起版本并标明Test已见；不自动追加模型回归。

最终简历只有实际支持时才写“同模型基线提升B个百分点、Token降低C%”。若未提升，可写公开基准适配、实测成功率、运行成本与可靠性结果，不以预设正收益作为项目完成条件。

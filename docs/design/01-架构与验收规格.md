# 架构、业务契约与验收规格

日期：2026-10-16。所有接口、路径和命令均为待实现契约。

## 1. V1 产品与默认模拟规则

模拟一家服饰鞋类商店，数据中有多个消费者、多个订单、多件商品及尺码/颜色变体。身份来自服务端预设演示会话；模型不能任意指定当前用户。V1 仅监听本机，不声称已有生产认证体系。

默认规则是项目自定义业务规范，不是对真实商家的政策或法律解释。实现前写入 `docs/business-contract.md` 与版本化配置，禁止为适配某道题临时改规则。

| 业务 | 默认规则 | V1 成功终态 |
|---|---|---|
| 订单查询 | 仅查看当前演示用户的订单 | 返回正确状态与商品，不改订单 |
| 取消订单 | 仅 `PAID_UNSHIPPED`；整单取消；无并发处理中售后 | 订单为 `CANCELLED`，记录模拟退款请求；不能声称退款到账 |
| 退货申请 | `DELIVERED`；交付后 7×24 小时内（边界含）；普通可退商品且未使用；商品数量未被其他活动申请占用 | `RETURN_REQUESTED`，创建售后申请；不变为已退款 |
| 换货申请 | 同一商品系列、等价变体；交付后 15×24 小时内（边界含）；未使用且可换；库存足够 | `EXCHANGE_REQUESTED`，创建申请及库存预留；不声称已寄出 |
| 缺货 | 用户明确授权的备选路径才能提出退货预览，否则澄清或转人工 | 新预览或转人工；禁止直接把换货变退货 |
| 超范围/疑似质量争议 | 不擅自认定；转人工 | `HANDOFF_PENDING` 工单与证据摘要 |
| 运费与金额 | 取消仅记录原支付额的模拟退款请求；退换运费由版本化政策确定；所有金额用整数分 | 操作卡片清楚展示，不让模型计算写库金额 |

退换 V1 每次只提交一个订单中的一个商品行和数量；同一对话可以依次处理多个订单。不存在“一次原子修改多个订单”的承诺。活动售后数量不得超过可申请数量；重叠退换申请必须由数据库事务拒绝。

时间由可注入的时钟提供。生产演示使用当前时间，测试固定时钟。时间计算用带时区 UTC，前端按 Asia/Shanghai 展示；到期按时间差而非随意取自然日。

政策选用规则明确区分：购物时承诺的资格政策随订单保存版本，申请流程规则使用申请时有效版本。任何被预览使用的政策版本变化均触发重新校验。语料与确定性资格规则必须一致，并做一致性测试；验收不能只调用被测资格函数验证自己。

## 2. 技术选择与范围

- Python 3.12 为优先兼容目标；阶段 0 检查本机与依赖后锁定一个明确版本，不擅自升级全局 Python。
- Deep Agents 主 Agent；LangGraph 持久化与中断。运行时一个主 Agent，无开放 shell、任意文件访问或通用子 Agent。
- FastAPI + Pydantic；SQLAlchemy + Alembic；PostgreSQL 作为唯一业务数据库与持久化基础。使用正式 PostgreSQL 做事务验收，不能以 SQLite 测试代替并发语义。
- pgvector 保存本地 embedding；BM25 用轻量 Python 实现。小语料先精确向量检索，不为简历强加复杂近似索引。
- 中文首版 embedding 默认 `BAAI/bge-small-zh-v1.5`，reranker 默认 `BAAI/bge-reranker-base`，均固定 revision。相较上一轮 BGE-M3 草案，默认改为更轻的中文模型，降低本机资源负担；BGE-M3 是后续可选对照，不改变检索接口。
- 本地模型先跑资源探针，报告下载量、内存、延迟；权重只进项目缓存。未下载时使用 BM25 和测试替身，但明确不声称完成向量语义验收。
- 前端使用 FastAPI 模板＋原生 TypeScript 或 JavaScript＋CSS，三栏布局即可；不引入复杂前端状态框架。静态资源本地提供。
- Docker Compose 管理 app、worker、PostgreSQL；不引入 Redis/Celery/Kafka。数据库任务队列＋一个 worker 即可。
- pytest 验证关键行为；ruff 做静态检查。普通测试禁止外部 LLM 网络请求。无需为每个 getter 写机械测试。

版本号由 Agent 在阶段 0 查兼容性后固定到锁文件。为可复现保留 Python、镜像 digest、模型权重 revision 与语料 hash。

## 5. 状态与事务约束

### 5.1 会话与任务

`IDLE → RUNNING → WAITING_USER / WAITING_CONFIRMATION → RUNNING → COMPLETED`。
另有 `CANCELLED / FAILED / HANDOFF_PENDING`。界面等待澄清与等待操作确认是不同状态。

同一会话只允许一个活跃 worker 执行；新用户消息先持久化、递增 intent_revision，再串行处理。不能让两个模型回合同时修改当前方案。

普通新消息到达时，保守地使当前待确认预览失效；V1 不从聊天“好的”推断授权。用户确认使用结构化按钮或明确的确认 API。这个选择会增加一次确认，但能避免误授权。

### 5.2 操作预览

`PENDING → CONFIRMED → COMMITTED`，或 `REJECTED / EXPIRED / INVALIDATED`。

有效期默认 10 分钟，可配置。确认绑定 principal、conversation、preview_id、参数 hash 与 intent_revision；前端只提交预览 ID 和决定，金额/权限由后端重新取值。

### 5.3 原子业务提交

一次 PostgreSQL 事务内：按稳定顺序锁定会话当前意图/预览、订单行及库存 → 查已有幂等回执 → 验证确认、参数与版本 → 重新检查资格和库存 → 修改订单/创建申请/预留库存 → 写 operation 回执和业务审计事件 → 提交。

同一幂等键配不同请求内容必须报 `IDEMPOTENCY_CONFLICT`；同一业务提交即使调用者换 key，也被 preview_id/operation 的唯一关系阻止重复。不能仅依赖“模型记得已操作”。

预览阶段不锁住库存等待用户。提交阶段重新检查，库存变化时返回 `STATE_CHANGED`，重新生成方案。退换申请中的库存预留到工单处理或显式取消才释放；不可在创建申请后静默超时释放却仍显示申请有效。

提交成功但 HTTP/工具响应丢失：operation 已落库，使用同一 preview/operation 查询回执。数据库结果不明时先查询，不重新造申请。外部真实支付/物流的跨系统事务不在 V1 范围内。

确认与“等等，我改主意”并发时，以数据库串行化后的已接受事件顺序为准。如果提交已完成，后来的撤销意图不能伪称回滚了已经完成的操作；返回实际状态并转入下一次处理。

### 5.4 checkpoint 与副作用

中断节点恢复可能重跑节点前半段，因此确认前不得放不可幂等的业务写操作。业务副作用用唯一操作 ID 保护。重复恢复、worker 重启、用户重复点击都必须返回已有结果或明确冲突。

一个 worker 进程执行有界任务。软取消先通知、关闭请求；超过清理期限由父进程终止，并保存 usage_unknown/任务状态。不能单凭 SDK timeout 参数声称有端到端截止；用阻塞假客户端做实际验收。

## 6. 工具接口：模型只能表达业务意图

所有工具返回统一 envelope：`ok, data, error_code, retryable, user_message, trace_id`。错误不能简单吞成空列表。

| 工具 | 模型可传参数 | 返回/限制 |
|---|---|---|
| list_orders | status_filter、时间范围 | 仅当前 principal 的订单摘要；限制返回量 |
| get_order | order_id | 订单/商品/当前状态及版本；越权与不存在不泄露他人数据 |
| get_inventory | product_id、variant_filters | 可用变体与库存快照，不保证提交时仍有库存 |
| search_policies | query、action、可选分类 | 后端结合当前订单选版本；返回 policy_ref、条款及适用条件 |
| update_case | 明确变更字段、对应 source_message_id | Pydantic 校验、来源核对、CAS revision；不能写 approval 或 principal |
| preview_action | action、order_id、line_id、quantity、target_variant、reason | 返回只读操作预览；金额、资格和版本由服务端计算 |
| commit_action | preview_id | 后端读取可信确认；模型无法传 approved/user_id/amount 绕过规则 |
| get_operation | operation_id 或 preview_id | 返回执行结果和状态，用于响应丢失恢复 |
| request_handoff | reason_code、简短摘要、相关已知 ID | 建本地待处理工单，禁止向外部邮箱/平台发送消息 |

内部运行上下文注入 principal、conversation_id、run_id 与预算；这些字段不交给模型填写。

Deep Agents 安装版本可能自动加入文件、规划、子 Agent 等工具。阶段 3 必须检查实际模型可见工具列表：仅放行上述业务工具；在调用分发层再次拒绝未授权工具。默认文件/backend 即使存在也只能是隔离虚拟状态。不得只靠提示词说“不要执行 shell”。

错误恢复采用分类：

- 输入缺失→澄清；无权限→拒绝；不符合政策→解释或转人工。
- 订单/库存/意图版本冲突→重新读取并生成预览，不重试旧确认。
- 临时读失败→最多两次有退避重试，计入总工具/时间预算。
- 写结果未知→查 operation；不能盲目再写。
- 模型 schema 错误→有限结构化反馈，最多两次，计入同一模型预算。
- 401、403、欠费、额度耗尽、身份错误→停止，不重试，不自动换模型。

## 7. HTTP API 契约

| 路由 | 用途 |
|---|---|
| GET /health/live、/health/ready | 活性/依赖就绪；不调用模型 |
| POST /api/demo-sessions | 选择预设演示用户并建立服务端身份，默认仅本机可用 |
| POST /api/conversations | 创建会话，返回 ID |
| POST /api/conversations/{id}/messages | 输入 text + client_message_id；去重并入队；返回 job_id |
| GET /api/conversations/{id} | 当前状态、消息与待确认预览 |
| GET /api/conversations/{id}/events | SSE；支持 Last-Event-ID 重放，不重跑业务 |
| POST /api/previews/{id}/confirm | accept/reject；校验归属、版本、有效期，记录确认并唤醒任务 |
| POST /api/jobs/{id}/cancel | 请求取消，返回真实执行边界 |
| GET /api/operations/{id} | 查询回执与状态 |
| GET /api/runs/{id}/trace | 脱敏的工具、证据、用量、状态事件 |

SSE 是展示通道，断线不等于取消。客户端重发消息用 message_id 去重；事件 ID 单调，断线重连不复制消息。确认 endpoint 应有同源/CSRF 防护，身份从服务端会话取，不能只信前端 hidden user_id。

后台 SSE 与 Trace 展示工具摘要和结果，不要求显示模型隐藏推理。模型说“已成功”而无 committed receipt 时，后端不能让 UI 显示完成。

## 8. 上下文与检索

### 8.1 有效状态

字段至少包括 `current_order_id, current_line_id, intent, constraints, missing_fields, evidence_refs, active_preview_id, intent_revision`；每条用户事实附 source_message_id，过时事实标记 superseded。不要把每段聊天摘要都永久写成事实。

上下文组成：系统边界＋当前有效状态＋最近若干完整消息＋本轮相关证据。工具调用与结果消息必须成对保存，压缩不能破坏协议。保留完整原始事件供回放，但不每次全部发模型。

向模型压缩历史属于真实模型调用，必须走同一个预算入口；V1 优先通过结构化状态与确定性裁剪控制成本，LLM 摘要作为独立可选配置。

### 8.2 政策语料

先建立约 20—30 份有明确适用条件的自定义模拟政策文档，包括取消、退换、尺码、运费、活动例外、时效、旧版与新版。不为凑量复制无关文本，不冒充真实企业内部数据。

每条款保留 title、section、source_id、version、effective_from/to、category、action、content_hash。按条款边界切分，使用实际 embedding tokenizer 控制长度，禁止静默截断例外条件；跨条款例外保留关联。

推荐初始检索参数：元数据预过滤→BM25 top20＋dense top20→RRF(k=60)→去重→rerank top10→返回 top5，另设最终上下文 Token 上限。参数只在开发集调节。BM25 中文分词策略固定并记录，不直接以空格分词中文。

订单/库存是工具数据，不能用知识库里的旧快照当实时事实。向量相似度、rerank 分数不能直接解释成“可执行置信度”。找不到适用条款时澄清或转人工。

查询重写优先拼接结构化字段；若加模型改写，必须单列消耗和消融。所有缓存键含模型 revision、语料 hash、政策版本与查询；正式评测记录冷/热缓存状态。

完整政策基线、BM25、dense、hybrid、hybrid+rerank 可配置。小语料全量政策可能更好，不能人为截断基线制造检索优势。

## 9. 可观察性与运行边界

Trace 保存消息 ID、工具名、脱敏参数、错误代码、政策引用、状态版本、操作 ID、模型用量和耗时。原始调试轨迹留在 runtime，发布时只导出审查后的模拟样例。

记录实际执行事件，不让模型生成“执行日志”。指标分为产品正确性、框架故障、模型行为、检索质量和成本，不能把所有失败归为模型差。

全局默认 `ALLOW_REAL_MODEL_CALLS=false`。创建客户端、导入模块、启动 Web、健康检查、普通 pytest 均不触发真实请求。每个模型路径，包括框架摘要中间件与辅助模型，统一经受控工厂和 BudgetLedger。

开发依赖下载不算模型请求，但需遵守用户批准的资源范围。模型服务不自动连公开搜索，不上传项目代码到辅助服务，不开启付费托管知识库。

## 10. 必须通过的行为验收

1. 不经过模型也能完成查询→预览→确认→提交，返回正确申请编号和真实状态。
2. 正常取消、退货、换货分别正确；临界时间、不可退分类和数量冲突有明确结果。
3. 用户换订单/商品/意图后旧确认失效；旧确认按钮不能执行新参数。
4. 模型伪造 approved/principal/金额、调用禁用工具均失败，并留事件。
5. 两个并发提交、重复点击、worker 重启恢复只产生一次业务副作用。
6. 库存竞争时不超卖、不变负数；预览后订单变为已发货则取消失败。
7. 提交成功但返回丢失，恢复能找回同一个 operation 和申请。
8. 数据库中途报错时申请、库存、回执、业务事件共同回滚。
9. SSE 断线重连与消息重发不引发重复执行；用户能看到回放结果。
10. checkpoint 恢复不等于重新授权；无授权、已失效授权和错用户授权都不能提交。
11. 使用旧政策、缺少例外条款、用户改口后保留旧约束等错误可被独立测试检出。
12. 阻塞模型替身、工具超时和取消能在端到端截止内清理，且不把未知用量算零。
13. 默认离线启动/检查/测试没有外部模型流量；预算满时发送请求前即拒绝。
14. 评测器能识别“最终数据库正确但先越权后恢复”的过程错误。
15. 受控删除关键保护的测试变体（只在测试内）会被验收检出，证明测试并非仅复述实现。

每个阶段只运行其相关检查；改动后跑必要回归。最终交付跑一次完整本地/容器验收并记录跳过项，不为增加数量编写没有行为意义的测试。

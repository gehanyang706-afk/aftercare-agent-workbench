# 模型额度、调用预算与独立评测

日期：2026-10-16。截图是本轮用户提供的额度快照，未登录账户核验。本文件只规划，不授权或执行 API 调用。

## 1. 先分开两类模型使用

**编程助手**负责写代码、测试和排查，使用其当前产品的额度。**项目运行模型**负责售后对话、工具调用、用户模拟等，使用本截图所示的百炼 API 额度。二者不能默认视为同一个额度池。

不需要为了写每个函数而再调用一遍百炼模型。大多数实现、业务测试、数据库并发和故障恢复验证，用编程助手＋本地脚本即可完成。

## 2. 截图含义及当前核实情况

可见的精确模型为 `tongyi-intent-detect-v3`、`qwen3.5-plus-2026-02-15`、`glm-5`、`qwen-max`、`qwen-mt-flash`、`qwen3.7-max-2026-06-08`、`glm-5.1`。截图各显示剩余 1M/共 1M，到期日为 2027-01-11。不能据此推断截图外其他模型额度。

右侧“未开启”指免费额度用完即停保护未开启，并非模型不可调用。用户在使用前应确认计划模型的保护状态。[官方用量说明](https://help.aliyun.com/zh/model-studio/model-usage-statistics)

免费额度按精确模型 ID 分开，输入输出共用；快照与别名不能随意互换。中国站文档所述免费额度适用北京地域，其他地域不能照搬。仅实时推理抵扣，Batch、训练及其他云资源不在同一抵扣范围。通用 API Key 与 Coding/Token Plan 专属 Key 不可混淆。[官方额度规则](https://help.aliyun.com/zh/model-studio/new-free-quota)

控制台用量并非实时逐请求同步。项目账本只能管理本项目调用，不能知道用户或其他应用是否同时消耗同一账号额度。每个大批次前人工刷新余量，批准上限不得超过核实后的可用量减保留量。

## 3. 模型分工与规划上限

下表是建议的首轮项目预算，不是已经授权的消耗量，也不是质量排名。可在试跑后缩小，不能未经批准扩大。

| 精确模型 ID | 角色 | 拟定使用上限 | 保留量（以截图 1M 为前提） |
|---|---|---:|---:|
| qwen3.5-plus-2026-02-15 | 主 Agent；同一模型上的基线/完整方案正式对照 | 150k 接口与开发试跑＋700k 正式评测 | 150k |
| glm-5 | 早期开发集联调、参数和工具恢复探索 | 600k | 400k |
| qwen-max | 小规模自适应用户模拟；提示词固定、保留原始对话 | 600k | 400k |
| glm-5.1 | 开发场景草稿、政策歧义审查与人工抽审辅助 | 250k | 750k |
| qwen3.7-max-2026-06-08 | 主实验后第二模型复验；前期尽量保留 | 750k | 250k |
| tongyi-intent-detect-v3 | 可选意图/槽位模型对比，非首版依赖 | 100k | 900k |
| qwen-mt-flash | 中文首版不使用；如将来翻译另开批次 | 0 | 1M |

`qwen-mt-flash` 是翻译模型，不能因为带 flash 就当通用便宜工具 Agent。[Qwen-MT API](https://help.aliyun.com/zh/model-studio/qwen-mt-api)

`tongyi-intent-detect-v3` 采用意图/槽位专用协议；不假设直接替换通用 chat/tool 模型。固定流程基线首先使用同一个主模型做意图抽取，避免同时换架构和模型影响归因。[意图理解能力](https://help.aliyun.com/zh/model-studio/intent-detect-capability)

主模型快照支持工具调用，但账户可调用性、客户端传参、usage 和流式行为需要小额验证。GLM 的思考/工具参数应在 provider capability 配置中单独处理，不能复制 Qwen 参数后假定等价。[Qwen 3.5 官方模型页](https://help.aliyun.com/zh/model-studio/qwen3-5-plus)、[GLM 官方说明](https://help.aliyun.com/zh/model-studio/glm)、[Function Calling](https://help.aliyun.com/zh/model-studio/qwen-function-calling)

`qwen-max` 是别名，记录请求模型、返回模型字段、日期与参数，不能声称权重永久固定。对照使用相同模拟器配置并交错运行，保留记录以分析漂移。

模型中途额度不足时暂停，不静默切换模型。不同模型的结果分别报告；“旧模型基线 vs 新模型完整方案”不能证明工程优化收益。

## 4. 凭据与客户端配置契约

使用当前账户北京业务空间的通用 API Key。当前官方示例的 Base URL 为：

```text
https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/compatible-mode/v1
```

`WorkspaceId` 从用户控制台取得，不凭空编造。已有兼容域名可按账户文档核对，程序不自动在多个地域/域名间试探。[首次 API 调用说明](https://help.aliyun.com/zh/model-studio/first-api-call-to-qwen)

拟实现 `.env.example`：

```dotenv
DASHSCOPE_API_KEY=
DASHSCOPE_BASE_URL=
ALLOW_REAL_MODEL_CALLS=false
DATABASE_URL=
APP_ENV=local
```

精确模型、思考模式、输出上限、工具参数放进 `configs/models.yaml`；角色分配与实验 profile 分开。Key 不写入 YAML，不打印进 doctor，不要求用户贴到对话。

provider 按模型核实 `enable_thinking`、`tool_stream`、JSON mode、stream usage 等参数。若能力不支持则明确报错或采用已记录的替代协议，不静默删掉重要参数。

GLM 工具调用当前文档有专属 `tool_stream` 要求；由适配器按锁定接口与小额契约测试落实。正式实验优先非思考模式，关闭方式必须经核实；若无法关闭，必须重新估算输出/思考消耗。[工具调用参数说明](https://help.aliyun.com/zh/model-studio/qwen-function-calling)

检索默认本地模型。截图没有证明 embedding/reranker API 免费额度，不额外申请付费托管检索服务。模型权重需要单独接受下载与本地资源占用。

## 5. 预算网关必须覆盖全部调用

`BudgetLedger` 按 `provider + exact_model_id + batch_id` 保存预算，另有项目累计与会话上限。禁止把不同模型额度合并到一个数字。

每次请求前，在 PostgreSQL 事务内预留：

```text
reservation = conservative_input_bound + enforced_output_cap
can_call = settled_usage + unresolved_reservations + reservation <= approved_cap
```

输入必须包含系统提示、全部历史、工具定义、工具返回和框架自动附加内容。若服务商输出上限不涵盖思考，则还需单独预留思考额度；无法可靠限制时不进入正式批次。

成功响应用实际 `usage.total_tokens` 结算。输入/输出可分列，但不要把 reasoning_tokens 再加到已包含它的 completion/total 上。流式调用按对应接口请求最终 usage。[API 用量字段](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions/)

失败、超时、断流若无 usage，记 `usage_unknown`，保留原预留并暂停该模型后续调用等待核对；不能释放为 0。任务是否成功与 Token 是否已消费是两件事。

所有重试都从统一入口重新预留，SDK 自动重试关闭。初期并发为 1。不得让框架摘要、隐藏纠错、用户模拟或评测辅助模型绕过账本。

本地估算不是服务商计费的数学保证；“用完即停”是账户层额外保护。每次请求保守预留、每阶段留余量、每批次前核对控制台，共同降低超额风险，不能承诺凭字符估算绝对零费用。

建议初始执行边界：每轮最多 8 次模型调用、每会话最多 16 次；工具失败最多恢复 2 次；一个自动处理片段 180 秒，不把等待用户时间算进模型执行超时；上下文与输出上限经试跑确定。所有上限是初始配置，若过严应在开发集调整并冻结，不在看过正式分数后改。

## 6. 真实调用分成三个批次

### A. 接口兼容性批次

只验证主模型：普通文字、工具调用、工具结果回传、流式 usage、结构化或可校验输出。初始上限建议 **8 次 HTTP 请求、20k 总 Token**，包含重试；不因某项失败无限重试。

试跑计划必须实际列出 prompts/tool schema、最大输入/输出与预留总量。若估计超过 20k，先减少样例或提交新的上限，不绕过限制。错误鉴权或免费额度保护错误直接停止。

### B. 开发集成本试跑

从开发集预先选择 4 个有代表性的场景，在基线和完整方案各跑一次，即 8 个完整会话；不是 8 个模型请求。

建议每会话暂设 12k 主模型总 Token；8 会话最坏 96k，再加 A 的 20k，仍在主模型 150k 开发总预算内。使用脚本用户优先，不先引入模拟器成本。

若 12k 导致正常流程普遍被截断，必须报告：是上下文过大、调用链冗余，还是任务确实需要更多。先修通用设计，再按预算调整题数/会话上限。不要为了“没超预算”宣称被截断任务已验收。

输出：每会话主模型总 Token 分布、请求数、工具调用、延迟、失败类型、usage 完整性及正式评测建议。

### C. 冻结成对评测

原先 100 题×2 配置×3 次的 600 会话计划不应直接启动。假设每会话 8k Token，则仅主模型就要 4.8M，超过截图里单模型 1M；8k 只是说明公式的示例，不是实测。

额度受限的参考批次：

- 从 100 个独立情景中按四类各抽 6 个，预先固定 **24 个不同任务**。
- 同一主模型、两个配置，各跑一次，共 48 个会话。
- 另预先选定 4 个任务各做一轮额外成对重复，共 8 个会话。
- 若开发集证明每会话 12k 上限足够，56×12k = **672k**，在 700k 正式预算内。
- 主结果分母为 24，不是 28 或 56。重复仅报告这 4 个任务的稳定性。

正式采用多少题取决于开发集实测；任务应按规则分层抽样，不能挑基线最差或最容易成功的题。12k 若不够，可减少题量并提高会话上限，需在正式跑前固定。

按任务对预留两个配置的预算，优先完成可比较的成对结果。预算不足时不启动新任务对；已有失败/超时必须进入结果。中途环境故障导致不可比，标记并保留，不伪装成正常模型失败或悄悄删除。

如果需要完整 100 题或更多重复，先用真实消耗计算新增 Token 和当前价格，向用户提出封顶费用批次；不能默认把个人项目锁死在免费额度内，也不能默认允许产生费用。第二模型复验独立成批、独立报告，不用其额度给第一模型的样本数“补账”。

## 7. 场景、用户模拟与答案隔离

### 7.1 数据集目标

拟建设 160 个业务情景：60 dev、100 holdout。四类分别为基础办理、多轮变更、政策/权限边界、故障恢复；各 40 个，按模板族安排 15 dev/25 holdout。相近措辞重写不能跨组充数。

情景数不是 pytest 测试数，也不是已完成真实会话数。报告分别列出：库中场景、离线验证、真实已跑独立任务、完整会话和模型调用。

政策语料本身允许产品 Agent 访问。隐藏的是任务目标细节、用户未来行为脚本、预期终态、禁止事件及评分答案；用户逐轮公开的信息按正常业务暴露。

### 7.2 情景格式

```text
scenario_id / family_id / category / split
seed / clock / fixture_reference
initial_user_message
hidden_user_goal / user_known_facts / user_behavior_policy
public_policy_manifest
fault_schedule                         # 例如提交后丢响应；不传给产品模型
expected_state_invariants
required_communications
forbidden_events
max_turns / stop_conditions
```

验收检查允许多种正确工具顺序，不要求完全复制参考轨迹。动态变化可按业务事件触发，例如首次生成预览后更新库存，而不是按固定第几轮对话强行触发。

### 7.3 两类用户模拟

脚本用户用于可控对照：按当前 Agent 提问和可观察状态提供订单/商品信息、纠错和确认。不能把一种方案生成的全部对话机械回放给另一种方案，忽略它问了不同问题。

模型用户用于少量真实性复验：固定 qwen-max 角色、目标、事实、可接受条件和提示词；不向它暴露完整答案或 Agent 内部日志。模型用户必须自己走可信确认入口，不能由产品 Agent 伪造批准。

用户模拟器偏离事实、擅自同意、卡住等单列为 simulator_invalid，保留轨迹。报告全部尝试与有效任务结果，按预先规则处理，不凭分数选择重跑。

### 7.4 独立性

实现 Agent 可以查看 dev。最终样本由独立评测角色按冻结业务契约编写并人工抽审，放在独立 evaluator 目录，产品容器不挂载。不是通过“换个模型给自己打分”获得独立性。

在同一台电脑上，这主要是工作流程与运行隔离，不是针对拥有宿主机权限的编程 Agent 的保密系统。必须用任务边界约束实现角色不读取 holdout；无法做到时如实称为已见评测，不伪称盲测。

验收器用独立状态断言和事件规则，不能把生产资格函数直接作为唯一 oracle。LLM 可辅助检查文字解释，但不能作为唯一正确性裁判。

正式评测后若查看具体答案并修复，该样本转为回归集；下一次泛化结论需要新留出样本。数据错误修订需要版本号、理由与旧结果保留。

## 8. 基线、消融与指标

开发阶段配置：

1. `fixed-workflow`：同一模型抽取意图/槽位，确定性流程；检验是否需要更灵活 Agent。
2. `react-full-policy`：相同工具和安全后端，完整政策＋可容纳的完整历史。
3. `retrieval`：主循环一致，只变检索上下文。
4. `full`：检索＋结构化有效状态＋有界恢复。

检索组件可离线比较 BM25/dense/hybrid/hybrid-rerank，不消耗主 LLM 额度。大规模正式对照只选事先确定的两组；完整逐组件消融先放开发集，不能把一组堆叠改动的收益全归于某单个组件。

各配置共享权限、确认、幂等和确定性业务规则，不通过关掉保护提升候选“安全性”。模型、预算、语料、初态、用户策略和工具相同；记忆对照保留强完整历史基线，超上下文时明确说明适用范围。

| 指标 | 定义与分母 |
|---|---|
| Task Success | 业务终态、过程授权与必要告知同时通过的任务数/尝试任务数；另列系统故障 |
| 可办理任务完成率 | 应自动办理任务中正确完成的比例，防止全转人工取得高分 |
| 拒绝/转人工正确性 | 应拒绝/转人工的召回与不必要拒绝比例，不能只报拒绝准确率 |
| 未授权尝试 | 出现未确认/越权写调用的任务数/适用任务数；被后端拦住仍算行为缺陷 |
| 错误实际副作用 | 错对象、重复申请、非法状态或多余写入的数量/任务数 |
| 状态保持率 | 需要保留或修改的关键字段中满足当前有效约束的比例；按长对话子集报告 |
| Recall@5 | 独立标注的相关条款在 top5 的召回；多条必要证据另报完整覆盖率 |
| 用量/成本 | 各模型 actual Token、未知预留、平均/中位；不合并不同价格为伪成本 |
| 延迟 | 模型/检索/工具分段及端到端，等待真人确认排除；P95 标明小样本不稳定 |
| 稳定性 | 同一预选任务重复运行全部通过的任务数/重复任务数，不能当普通 pass@k |

输出逐任务成对结果，给绝对 n/N 和百分点差异。样本很少时不强调统计显著性；任务重复会话不是互相独立的新题。

目标如成功率 80%、输入 Token 降低 25% 仅用于规划，不是退出失败评测或刷题的标准。若没有提升，报告原因和取舍；成本下降但成功率不降同样有价值。

## 9. 每次调用与每次实验的记录

调用至少记录 request_id、requested/returned model、batch/run/task ID（task ID 不入模型上下文）、输入输出/总用量、思考细项、参数、开始结束、错误、预算预留/结算。

实验 manifest 至少包含代码 commit 或工作树内容 hash、依赖锁 hash、镜像 digest、语料/模型权重/任务版本、场景抽样规则、模型精确 ID、用户模拟器、提示词 hash、上下文与工具/Token/时间预算、缓存策略。

重放记录是历史回放，不是重新调用模型；必须区别 offline replay 与 fresh inference。报告不得把缓存答案当新的一次成功试验。

## 10. 用户授权模板

先让 Agent 给出已填好、可审阅的计划。不要让用户自己计算每个请求。

```text
我已确认北京地域通用 API Key 和精确模型余量，并开启计划模型的免费额度用完即停。
批准批次：<batch_id>，计划文件：<绝对路径>。
精确模型：<model_id>。
场景/请求清单：<manifest 绝对路径或固定条目>。
上限：<总 Token>、<最大请求数>、<每会话上限>、<最长执行时间>，最大并发 1。
本次最多允许额外付费：0 元 / <明确金额>。
达到任一限制、出现未知用量或额度/鉴权异常即停止，不自动换模型或续批。
在该范围内自主完成调用、记录、必要开发修复和报告，不需要逐请求问我。
```

“批准”不能仅由程序从文件名猜测；用户消息与计划 hash 进入审计记录。控制台保护、代码预算与用户批准是不同层次，缺一不能宣称调用边界已落实。

设计日期：2026-10-16。状态：设计交付，尚未实现。

这套材料供用户逐阶段交给编程 Agent 执行。本轮只生成设计文档，没有创建业务项目、安装依赖、下载模型或调用真实模型。

## 1. 项目目标

项目名：**电商售后多轮决策与执行 Agent 工作台**。

拟建目录：`/Users/gehanyang/编程/aftercare-agent-workbench`。该目录是后续实现位置，不是本轮已交付的软件。

目标用户是模拟商户的消费者与客服人员。系统理解自然语言诉求，查询订单与库存，检索适用政策，澄清缺失信息，生成操作预览，经用户明确确认后提交取消订单、退货申请或换货申请；不能处理时创建人工接管工单。

核心价值：多轮诉求变更时仍处理正确对象，业务执行可确认、可恢复、可验收。V1 不连接真实商户、支付、物流或消息平台，不把“提交退换申请”写成“已退款/已完成换货”。

## 3. 用户与 Agent 的分工

工程实现、测试、数据库迁移、前端、Docker、日志、故障复现、文档和实验脚本，默认由编程 Agent 完成。用户不需要手写这些代码，也不需要逐文件批准。

用户保留五项职责：

1. **产品判断。** 接受或调整本任务书中的模拟售后规则。默认接受即可，不必自行设计规则引擎。
2. **账号与资源。** 自己配置 API Key，确认地域和精确模型额度，开启免费额度用完即停；接受约定范围的本地依赖/权重下载。
3. **模型批次。** 根据 Agent 提供的具体调用清单、Token 上限和停止条件，授权一次试跑或正式评测；不授权无限循环调用。
4. **语义抽查。** 体验少量正常、改口、异常场景，判断理解、解释和确认卡片是否合理。数据与报告整理由 Agent 做。
5. **掌握与演示。** 能讲清用户输入到工具、业务服务、数据库和返回结果的链路，能独立演示一个正常案例与两个失败恢复案例。

每阶段安排一次约 20—40 分钟的体验和讲解作为起点；这只是交接安排，不是“几小时就能掌握所有代码”的承诺。面试理解需要额外复盘。

## 5. 实现 Agent 必须遵守的协作规则

- 当前阶段已经授权的代码、修复、测试与文档，自主做完。禁止把普通 bug 转成用户作业。
- 不为凑简历加入多 Agent 群、消息队列集群、微服务、模型训练或生产级多租户系统。
- 所有模拟效果与真实模型效果分开。脚本模型通过证明接口与流程，不证明模型能理解自然语言。
- 不把目标指标写成实测成果。测试数量仅体现覆盖面，不能替代业务任务成功率。
- 不识别评测任务 ID、不读取答案文件进提示词、不添加任务特判、不改评分标准来提高成绩。
- 不复制其他项目的密钥、运行数据库或用户资料。若复用已有模块，说明来源，复制后测试，不改源项目。
- 实际版本以阶段 0 锁定的依赖为准。先检查安装的框架 API/源码，再写适配；不能按记忆伪造参数。
- 真实调用、全局安装、额外大型下载、公网部署、公开发布和范围变更，给出具体方案后再等待用户决定。已批准批次内无需重复确认每次调用。
- 项目配置和日志不得出现明文密钥。不要让用户把 Key 发到聊天；只报告配置是否存在和连接结果。
- 发生评测失败时先定位原因。完整开发集可以用于修复；已查看答案的独立样本要转为回归样本，不能继续当未见样本宣称泛化。

## 6. 用户按阶段需要做什么

| 时间点 | 用户行动 | Agent 应交付的帮助 |
|---|---|---|
| 开始前 | 确认单商户、模拟数据、取消/退换申请这一范围；选择逐阶段或连续离线开发 | 已给默认规则，无需从零写 PRD |
| 阶段 0 后 | 确认本机能启动隔离环境；需要时自己启动 Docker Desktop | 环境诊断、缺项、精确启动命令 |
| 阶段 1 后 | 体验一笔取消、一笔换货、一笔重复提交 | 可直接执行的离线 demo 和解释 |
| 阶段 2—3 后 | 理解“有效诉求状态”和“操作确认”如何分开；看一条工具 Trace | 两张数据流图或等价说明、相关代码定位 |
| 阶段 4 后 | 在浏览器中途改口、刷新、重复确认、模拟响应丢失 | 三到五个稳定可复现演示入口 |
| 首次真实调用前 | 在北京地域确认 Key/业务空间/模型余量，开启用完即停，填入本地 .env；批准小额批次 | 不含密钥的检查工具、完整试跑清单和上限 |
| 正式评测前 | 看试跑实际用量，决定样本数与预算；抽查评测政策是否无歧义 | 冻结配置、抽样规则、预算估算和停止条件 |
| 最终交付 | 独立做一次约 10 分钟演示，解释三个机制；审核简历中的实际数字 | 干净环境运行说明、结果报告、面试讲解稿 |

## 7. 最低掌握清单

无需背所有文件，但要能回答以下问题并指出代码入口：

1. 为什么需要 Agent？哪些复杂诉求比“意图识别＋固定流程”更适合工具选择循环？
2. 工具调用的 JSON 从哪里来，如何校验，如何变成数据库操作？
3. 用户说“不是这单”后，哪个状态更新，哪个旧预览失效？
4. 为什么模型不能自己传一个 `approved=true` 就提交？
5. 提交成功但响应丢失时，为什么重试不会创建第二张申请？
6. checkpoint 和业务数据库事务分别保证什么，为什么二者不是一回事？
7. BM25、向量、RRF、重排各自解决什么，为什么还保留完整政策基线？
8. 为什么最终状态正确仍可能算失败？如何检查过程中的未授权尝试？
9. 预算如何覆盖历史、工具 schema、重试、摘要调用和 usage 缺失？
10. 哪个指标是实测，分母是什么，哪个结论仅来自小样本？

## 8. 交付边界

完整交付应包含可运行应用、模拟业务数据、可重放故障、测试、依赖锁定、Docker 环境、预算账本、评测报告与面试材料。公开基准适配是后续增强，不得拖住核心交付。

本设计没有承诺真实用户规模、生产上线、真实退款、100% 安全或固定提升幅度。真实结果由后续实验产生。

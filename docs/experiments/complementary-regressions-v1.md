## 预算停止为什么发生在实际23,437 Token

原checkpoint只读检查 next=('model',)：业务提交已完成，图还想调用模型说最后一句。
当前预算算法为请求完整UTF-8字节长度+1024输入预留+512输出上限；未把估算当实际usage。
按原checkpoint、相同投影中间件和九工具描述离线重建被拒请求（未发送）：

- 请求7,526字节；输入预留8,550，输出512，合计9,062。
- 已知23,437 + 9,062 = **32,499 > 32,000**，比上限多499，因此本地预留拒绝。
- 没有第12次HTTP，也没有新ModelCall行或未知预留。实际剩余8,563小于完整预留需求，不能据此取消保护继续调用。

两组总39请求，输入79,324 / 输出2,703 = **82,027 Token**；未知0。两批运行耗时合计190.731秒，不含人工核对间隔。

## 归因、实际输入比较与离线修复

两组封存后才进行离线修改。成功的r1-d-003/r1-d-048与失败的q1-A实际请求拥有**相同系统指令hash、相同工具schema hash**；订单商品行和库存工具结果均完整送达，缺陷不是上下文丢失或切换配置。
关键差异：前两题用户明确1件，q1-A用户没说数量；模型写入与订单购买数相同的2件并尝试预览，受到用户证据门禁后才转向澄清。可检验假设是购买数量被当作默认申请量；轨迹直接证实的是“没有用户数量依据”，不能据此读取模型内部推理。本轮没有再次出现“明确数量却重复追问”，因此没有继续追加提示词，也没有准备原四题重跑。

q1-A有两个不同问题：
1. 模型过程问题：缺少用户数量时使用购买数量猜测。服务保护成功，但行为仍不满足先澄清要求；后续多样表达优先观察，不改评分或临时加脚本回复。
2. 系统收尾问题：HITL graph.invoke包住“提交→模型告知”，提交后模型预留异常直接抛出，使应用来不及查询回执和保存最终告知。

最小通用修复只覆盖第二项：对本地预发送的CONVERSATION_TOKEN_LIMIT/BUDGET_EXHAUSTED/MODEL_CALL_LIMIT/BATCH_REQUEST_LIMIT，先查**同一已批准preview**的实际回执；确有回执才保存canonical最终告知，标记图STOPPED、业务COMPLETED，并返回execution_stop。没有回执仍抛原停止异常，绝不补提交。
评测actor继续返回ok=false和原停止码，runner必须停止后续题且保留失败；不会通过吞异常把预算停止变成评分通过。工作台同样的runtime负责告知，Job保存停止元数据。
不捕获并降级provider协议/usage/安全异常，不改BudgetLedger，不降低字节预留，不增加真实请求。本轮原q1-A结果与缺失告知原样保留，不补写旧成绩。

修复前4个预算停止反例失败、协议异常反例通过；修复后7项针对性测试通过，包括无回执不伪造、重复批准不重复副作用、实际API→队列共享runtime、停止码传给评测入口。

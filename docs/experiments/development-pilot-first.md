## 首次失败轨迹与分类

**d-001：模型工具依赖顺序 + 应用流程保护不足。**
实际 get_order → preview_action(PENDING) → update_case(INVALIDATED) → commit_action 提议。
业务工具按约使旧预览失效；图在 commit 前中断，没有可信批准，也未进入提交服务。
脚本用户找不到有效待确认卡而安全结束。不是支付/数据库故障；也不能因没有副作用就说模型没有缺陷。

**其余三题：数量歧义、模型推断与脚本用户缺口共同作用。**
原句“S1002 换大一码”没有声明件数。订单购买数量为 2，模型据此申请 2 件，目标库存只有 1，
业务工具正确返回 OUT_OF_STOCK。模型把“用户申请 2 件”作为事实告知，属于未经确认的数量推断。
原开发场景的成功预期事实上依赖工具默认 1 件，但隐藏目标没有明确数量，脚本用户也没有数量澄清回复分支。
因此不能将这三题完全归因于模型，也不能通过把库存改为 2、降低评分或现场重跑掩盖问题。
d-016 的改口、d-048 的恢复均 **未进入**；这不是一次已触发恢复后的失败结论。
